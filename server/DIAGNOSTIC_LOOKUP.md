# Controlled control-lookup diagnostic

This default-disabled feature is for a dedicated owned load-test app. It is not production caching or production write-event invalidation. Do not enable it on a shared or customer app.

The Orbit launcher injects its existing RedisConfig async client. The standalone server does not import Orbit or cache authorization. Without GALILEO_REDIS_HOST, Orbit does not construct a Redis client and database lookup remains available. Authentication and runtime-use authorization run on every evaluation, including Redis hits. The Redis connection is closed by the launcher lifespan.

Enable AGENT_CONTROL_LOOKUP_DIAGNOSTIC_ENABLED only with an explicit AGENT_CONTROL_LOOKUP_DIAGNOSTIC_FIXTURES list and timezone-aware AGENT_CONTROL_LOOKUP_DIAGNOSTIC_EXPIRES_AT. Each fixture contains namespace, agent, target_type, target_id, generation, and controls_sha256. Compute the digest over ordered parsed runtime controls with definition_digest and verify it against fresh read-only fixture evidence before deployment. Duplicate target identities can declare distinct reviewed pair generations. Never put identifiers or contents in metric labels.

Both modes use the same app image. Send X-LT-Control-Lookup-Cache as off or on and X-LT-Control-Lookup-Generation as the exact allowlisted pair generation. Without both headers the request is rejected; without either the original lookup path remains. Unknown/foreign/expired fixtures are rejected. Use a new reviewed generation for each comparison pair to prevent prior tests warming later pairs. Do not add excluded warmup traffic.

OFF queries the database for the agent and effective controls, then parses the definitions. ON reads serialized runtime definitions from a versioned, hashed Redis key. It validates their digest and returns independently parsed models. A miss uses the same database loader and writes a bounded JSON value with a 300-second TTL. No ORM objects, results, authorization decisions or model outputs are cached. No pickle, global scan or global Redis cleanup is used.

Every Redis command is bounded by the default 50ms deadline. A failed read, invalid cached value or timeout uses the DB path. A failed SET keeps the fresh DB result. The metric fallback counters must expose these cases; a passing semantic request does not prove a cache hit. Cache hits do not queue behind local locks. Local locks only coalesce misses within one process. They do not promise a single DB load across all replicas.

While this diagnostic is enabled, its middleware rejects POST/PUT/PATCH/DELETE configuration operations under agents, controls, control-bindings and policies. This freezes the dedicated application, including after cache expiry, until the diagnostic is disabled or the original app restored. Reads, evaluation, token exchange and observation remain available. No external/direct database writer may change the fixtures. A rejected write or changed fixture blocks further load. Capture the original app digest before deployment and restore it after the test.

Counter labels publish explicit startup zeros so missing series cannot be mistaken for no fallbacks. Numeric metrics are agent_control_lookup_diagnostic_seconds (mode and stage), agent_control_lookup_diagnostic_events_total (mode and outcome), and agent_control_lookup_diagnostic_sql_total (mode and query). Stages include authorization, pool_acquire, agent_query, effective_query, parse, control_load, redis_get, redis_set, cache_encode, cache_decode, engine and handler. Handler timing excludes authorization and response transport; use load-generator and existing HTTP middleware metrics for complete request latency. Query counters count attempted control-loader execute calls; they do not count authorization, pre-ping or every database operation.

Accept the live treatment only with verified Redis hits, fewer loader SQL calls, unchanged control matches and zero failures, original SLOs, source/image/resource proof and required connected traces. Compare cold and steady windows and retain misses. Histograms are independent distributions and cannot be subtracted to reconstruct request timing. A single OFF/ON pair is exploratory and does not prove a causal bottleneck or capacity boundary.
